## 1. 产品目标

Praxis 同时提供纯对话 ChatBot 和能够实际完成本地任务的 Agent。用户可以要求解释问题、生成代码，也可以委托 Agent 在指定项目中检查代码、修改文件、执行验证并持续推进长任务。

第一版以独立客户端使用为主，提供统一的平台认证。未来增加租户与平台执行能力，同一会话允许一个客户端控制，其他客户端只读观察。

## 3. 范围与非目标

第一版完成两条闭环：

1. ChatBot：登录、选择模型、持续多轮对话、流式展示回答、查询历史。
2. Agent：认证、选择本地项目、提交任务、检索及修改文件、执行命令、观察结果、追加指导、取消、保存和继续会话。

长任务表示一次任务可以包含多个模型请求及工具执行，并通过上下文管理持续推进；不是无限运行或承诺所有任务都能完成。遇到执行上限、权限拒绝、模型故障或无法判断的结果时，应明确停止或请求输入。

本轮新增 MCP 详细设计，提议作为第一版 Agent 的可选接入模块：支持本地 stdio、远程 Streamable HTTP、按需工具、文本资源及用户选择模板。高级 MCP Tasks/sampling/Apps 等不自动纳入；Praxis 不对外充当 MCP Server。完整能力矩阵见第 12 节所链接文档。

第一版不实现租户管理、云端 Agent 执行、多端控制权转移、无人值守调度、计费、不受信任 Host 插件的隔离加载、复杂工作流设计器或多 Agent 协作。插件先面向内置和明确受信任的扩展。本地命令及其子进程的操作系统沙箱属于第一版范围；它不等于可安全加载任意同进程插件，也不承诺虚拟机级隔离。

不可接受的结果包括：ChatBot 暗中执行本地操作；工具失败却报告成功；退出后残留由 Praxis 管理的任务；压缩删除原始历史；恢复过程盲目重复副作用；凭据进入模型上下文或普通日志。

## 4. 架构方案与选择

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A | Agent Runtime 嵌入桌面主进程或 CLI 主进程 | 启动简单，但入口与执行共享故障和资源边界。 |
| B，已选择 | 桌面和 CLI 启动、管理各自的 Agent Host 子进程 | 增加进程通信和清理工作，换取统一执行边界及未来远程接入能力。 |

服务端 ChatBot 使用模块化单体。方案 B 的独立进程承载本地 Agent；为落实客户端直连，提议桌面 ChatRuntime 也在同一个本地 Host 中运行。不要求把认证、ChatBot 和数据库拆成微服务，也不意味着每个会话启动一个进程。

部署关系：

```text
Web ───── HTTPS ── Praxis Server
                       ├── 用户、认证、Praxis API Key
                       ├── 统一用户模型配置与加密凭据
                       └── Web ChatRuntime / 历史 → 模型厂商

桌面主进程 ── 私有 stdio ── Desktop Host
                               ├── ChatRuntime（无操作工具）
                               └── AgentRuntime ─┐
CLI 主进程 ── 私有 stdio ── CLI Host             │
                               └── AgentRuntime ┤
                                                ├── 各自本地 Session
                                                ├── 工具、权限、插件、OS 沙箱
                                                └── 用户工作目录

各本地 Host ── HTTPS ── Praxis Server（仅身份、配置、凭据）
各本地 Host ── HTTPS ── 模型厂商（直接推理请求）
```

身份认证、Agent 执行位置、模型请求路由是三个独立边界。第一版本地客户端不使用 Praxis 模型网关；桌面 ChatBot 与 Agent 共用配置和 Host 的基础设施，但 ChatRuntime 不挂载 Agent 工具。各端会话仍独立保存。

## 5. 进程与生命周期

### 5.1 宿主关系

桌面主进程管理窗口、凭据桥接和一个本地 Host；该 Host 可承载多个本地会话。CLI 每次启动管理自己的 Host。两者共享代码和协议，不共享进程、运行中的会话或 SQLite 数据库。

Host 启动握手声明协议版本、父进程实例、能力和数据目录，并报告当前系统沙箱后端、支持的限制及可用状态。第一版使用私有 stdio 消息通道，不监听公共 TCP 端口。stdout 只承载协议，诊断写 stderr。父进程控制 Host 可执行文件及启动参数，不能从模型输出决定它们。

### 5.2 正常退出

1. 父进程停止接收新任务，发送 `host/shutdown`。
2. Host 停止接纳新 turn，保存取消意图并触发执行取消信号。
3. 模型适配器中止请求；工具执行器停止其管理的命令、MCP stdio 服务和子进程，取消远程 MCP 请求。
4. 保存已确认的工具结果、未知结果及任务终态，刷新存储。
5. Host 返回退出确认并退出；超时后父进程强制结束受管理的执行进程。

进程组、Job Object 等清理实现按操作系统适配。普通独立子进程不自动提供完整的进程树清理或文件权限隔离。第一版不提供工具主动脱离管理长期运行的能力。

提议退出宽限期为 5 秒，可配置。已写入的文件不会因为退出自动回滚。强制结束时不能伪造工具“取消成功”；下次启动识别未完整记录的运行。

该退出规则控制本地受管执行；外部 HTTP MCP 服务本身及已经提交的远端效果不受本机进程管理。取消响应不明时记录 unknown，不宣称撤回远端操作；第一版不协商脱离调用长期运行的 MCP Tasks。

### 5.3 异常与窗口关闭

Host 监测父进程通道关闭及心跳丢失，执行相同清理；父进程崩溃也不能把 Host 当作守护进程保留下来。无法存活执行清理的系统级故障，通过下次启动的恢复流程处理。

提议桌面端关闭最后一个工作窗口即退出该应用实例并停止全部 Agent 任务，包括 macOS；切换会话、切换 ChatBot/Agent、最小化窗口不等于退出。不通过隐藏托盘维持任务。

Web 无本地 Agent Host。用户关闭页面时只取消该页面拥有的 ChatBot 生成请求，不关闭服务器。以服务端连接断开检测为主、客户端取消请求为辅助，并设置生成时限，不能只依赖页面卸载事件。

## 6. 身份与模型配置

### 6.1 两类凭据

| 凭据 | 接收方 | 用途 | 建议存储 |
| --- | --- | --- | --- |
| Praxis 登录会话 | Praxis Server | Web / 桌面账号认证 | Web 使用 HttpOnly 安全 Cookie；桌面使用系统凭据存储 |
| Praxis API Key | Praxis Server | 桌面 / CLI 非交互认证 | 本机凭据存储或环境变量；服务端仅保存摘要及管理元数据 |
| 统一模型厂商 API Key | 对应模型厂商 | ChatBot 与 Agent 共用的模型调用凭据 | 服务端统一加密保存；本地 Host 通过专用接口取用，仅在内存保存当前 turn 所需值 |

Praxis 管理的认证和模型密钥不得由配置、凭据桥接或日志流程写入对话消息、工具参数、Session 事件或可导出的普通配置；配置引用 `credentialRef`。子进程只得到执行所需的环境，不继承宿主全部认证材料。

此承诺不等于对用户任意文件和命令输出提供完整的数据泄漏检测。已知凭据值在工具输出进入模型、记录或界面前脱敏，默认阻止读取 Praxis 凭据文件及常见敏感配置；陌生格式或用户主动粘贴的秘密无法保证全部识别，不能将自动脱敏宣传为任意内容的保密保证。

Praxis API Key 提议包含标识前缀和随机秘密，只在创建时显示完整值；用户可列出、吊销和重新签发自己的 Key。认证响应返回用户身份和有效期等必要信息，不返回厂商密钥。

### 6.2 认证有效期提案

本地客户端要求先完成 Praxis 认证，即使用户使用自己的模型厂商 Key。认证后取得短时身份凭证；每个新 turn 仍需通过专用 begin-use 接口在线核验身份与配置版本并取得当次厂商凭据。不能凭旧缓存绕过配置禁用。刷新或配置服务不可用时不启动新 turn，已接纳输入可排队并说明原因。

提议身份凭证有效期为 15 分钟，吊销在下一次 begin-use 检查时阻止新 turn；不是中断活动 turn 的时间保证。活动 turn 即使跨过凭证有效期，也可在自身执行预算内继续，退出和用户取消仍立即触发停止流程。第一版不做远程强制终止既有 turn，也不声称能收回已交付给本机的厂商 Key。仅有厂商 Key 不能绕过 Praxis 身份认证。

### 6.3 登录与账号初期范围提案

服务端提供单用户身份维度，不引入租户。提议以管理员创建账号、用户密码登录和用户自助签发 Praxis API Key 起步，暂不做公开注册、邮件找回或第三方登录。账号创建和密码重置必须有受控的管理入口。

这是待确认的交付范围，并非用户已指定的认证实现。

### 6.4 模型接入

统一 `ModelProvider` 接口支持消息、工具定义、流式增量、结束原因、用量和取消信号。每个适配器声明工具调用、上下文窗口等能力，不能因为使用同类 HTTP 接口就假定能力相同。

第一版提议先支持 DeepSeek，并保留扩展其他厂商的接口；不承诺任意填写 base URL 就能兼容所有模型。Agent 选用支持工具调用的模型，ChatBot 不发送工具定义。模型和凭据变更在下一个 turn 生效，活动 turn 固定自己的配置快照。

模型配置按用户管理，不按 ChatBot / Agent 或客户端安装实例拆分。同一用户在任一支持配置的入口填写一次提供商及 Key 后，其他入口取得同一配置，无需再填写一份。更新和删除也作用于同一配置；不得维护两份可各自编辑但互相冲突的模式专属 Key。

统一配置建议表示为 `ProviderConfig`，包含 `id`、`ownerUserId`、`providerType`、`baseUrl`、`credentialRef`、默认模型和配置版本。ChatBot 与 Agent 引用同一个 `providerConfigId`；它们可以选择不同模型，但同一提供商的认证材料不重复配置。配置共享不意味着模型一定具备 Agent 所需的工具调用能力，也不授予 ChatBot 执行工具的权限。

设置界面统一命名为“模型提供商”，显示提供商、可用模型、Key 已配置状态和必要的掩码，不提供“ChatBot Key / Agent Key”两个入口。Praxis API Key 保留在账号认证设置中。

服务端作为配置和加密凭据的权威存储，主密钥独立于数据库；各端可维护同一配置，修改携带版本，冲突不静默覆盖。普通设置查询只返回元数据和 Key 已配置状态。

本地 Host 在开始 turn 前通过专用凭据通道取得该用户当次配置快照和 Key，直接请求已验证的厂商端点，不经过 Praxis 模型网关。Web ChatRuntime 在服务端取用同一凭据。凭据不经普通设置读回、不转发给桌面 renderer、不持久化为第二份本地厂商配置。

具体接口、配置删除与轮换、重试和用量、账号与秘密存储见[模型、认证与统一配置设计](2026-11-02-praxis-model-auth-design.md)。统一配置和本地直连已确认；专用交付通道及内存生命周期是落实它们的设计方案。

## 7. ChatBot 运行方式

ChatBot 使用独立的 `ChatRuntime`，不装载文件、命令或其他操作型工具执行器。一个用户 turn 的正常流程为：接纳用户消息、选取历史、构建上下文、请求模型、流式返回、保存终态。

同一 ChatRuntime 在 Web 服务端和桌面本地 Host 分别组装，保持相同无工具边界；模型请求位置遵循第 4 节。重新生成、候选选择、断流与页面生命周期见[Chat 与协议详细设计](2026-11-02-praxis-protocol-chat-design.md)。

可见输出支持 Markdown、代码高亮和代码复制。第一版不执行模型生成的 HTML/JS，也不把它嵌入有本地权限的页面预览。用户复制代码后自行保存、运行。

每个会话同一时刻最多一个生成请求；重复的请求 ID 返回同一接纳结果。第一版遇到另一条并发生成请求返回 busy，由用户停止后重新提交，不实现 ChatBot 的 steer 队列。

断流时保存已确认的部分回复并标记 interrupted；完整回复、错误和中断状态不能混淆。重试生成是一次显式新操作，不把同一网络请求重复记成两条用户输入。

长期聊天依然需要上下文预算；超限时可以生成摘要，但不开放文件工具，不删除原始聊天记录。摘要失败时明确停止本次生成或要求新建会话，不静默丢弃关键历史。

## 8. Agent 的领域与状态

### 8.1 核心对象

| 对象 | 职责 |
| --- | --- |
| Workspace | 用户选定的本地项目目录及工具边界 |
| Session | 一段持续会话，含身份归属、事件历史、上下文版本和待处理输入 |
| Turn | 处理一次任务输入的一轮执行，可包含多个 step |
| Step | 一次模型决策及其工具执行阶段，协议重试可在此阶段内发生 |
| ToolCall | 具有稳定 ID、参数、审批和执行状态的工具调用 |
| Artifact | 修改或生成的文件、较大的工具输出及其引用 |

会话带 `kind: chat | agent`，创建后不直接切换类型。将 ChatBot 的代码交给 Agent 时创建独立 Agent 会话，显式复制所选需求，不将文本回答伪装成已执行的操作。

### 8.2 调度

同一个 Agent Session 只有一个推进状态的执行循环；不同 Session 可以并发。所有修改状态的命令经该 Session 的串行调度入口，包括 prompt、steer、cancel 和审批响应。

`queue` 等当前 turn 结束后开始新 turn；`steer` 在后续 step 的领取边界加入当前执行，不修改已经发出的模型请求、不自动中断正在运行的工具。无活动 turn 时两者都可以开始一轮任务。

第一版工具按模型返回顺序串行执行，以简化文件修改语义。跨会话修改同一 Workspace 时，提议在每个 Host 内限制一个可写 Agent Session；桌面和 CLI 同时打开同一项目则使用操作系统可释放的工作目录占用锁。冲突时说明占用者，不能只靠数据库分开来假定文件也隔离。

命令工具可先返回运行句柄，进程继续受当前 turn 管理；这不代表后续文件修改可与它任意并发。提议每会话最多一个活动命令，期间允许读、查询、计划和提问，阻止新的命令及专用文件写入。turn 收尾停止尚未完成的命令，第一版不提供最终回答后继续运行的会话级开发服务器；具体规则见内置工具详细设计。

MCP stdio 操作与命令共用外部执行位，从程序启动前持有到子孙清理后释放，不能在命令运行期间再启动 MCP 程序。HTTP MCP 调用仍按工具顺序执行，其结果和外部效果单独记录。

### 8.3 执行状态

执行状态为 `idle`、`running`、`waiting_approval`、`waiting_input`、`cancelling`、`interrupted`；每个 turn 单独记录 `completed`、`cancelled`、`failed`、`interrupted` 等结果。等待用户补充需求使用 `waiting_input`，等待具体操作授权使用 `waiting_approval`，不混为同一种批准。

任务达到模型请求次数、耗时或 token 预算上限时停止并说明原因。提议每 turn 100 个逻辑 step、150 次总模型尝试（含摘要与重试）、200 次工具调用及 60 分钟墙钟时间；细则见[执行核心详细设计](2026-11-02-praxis-runtime-session-design.md)。

## 9. 工具与权限

### 9.1 职责与执行入口

真实操作系统沙箱是已确认的要求；以下权限预设、工具命名和平台后端是围绕该要求的实现提案。Agent Host 是执行与授权的权威，桌面渲染层和 CLI 负责展示、提交用户决定，模型不能批准自己的调用。

| 组件 | 职责 |
| --- | --- |
| Tool Registry / Executor | 注册工具、校验参数、调度、取消及记录结果 |
| Permission Policy | 根据会话、工具、资源范围和已批准授权，决定允许、拒绝或申请权限 |
| Approval Service | 发起并记录审批；核验用户答复，仅生成范围明确的单次授权 |
| Sandbox Backend | 将本次命令的执行策略落实为操作系统限制，报告实际生效能力 |

调用路径为：工具参数校验 → 解析本次策略 → 必要时审批 → 持久化执行意图 → 文件执行器或系统沙箱命令执行器 → 记录结果。所有内置命令工具及可信插件通过 SDK 请求的命令都走同一执行入口；修改 cwd、改用另一种 Shell 或使用解释器不能绕过该入口。

### 9.2 权限预设与审批策略

参考 DSH，将用户选择的预设与底层的沙箱模式、审批策略分开。提议提供以下三种预设，实际默认值与完全访问入口在全文评审时确认：

| 预设 | 文件沙箱策略 | 审批策略 | 行为 |
| --- | --- | --- | --- |
| 只读 | `read-only` | `ask` | 可以执行命令，默认禁止持久文件修改；需要写入时申请单次授权 |
| 工作区可写，建议默认 | `workspace-write` | `ask` | 在已授予的读写范围内自动执行；扩大范围时审批 |
| 完全访问，显式选择 | `danger-full-access` | `never` | 关闭相应操作的文件沙箱限制；界面明确显示关闭状态，不因执行失败自动切换 |

`ask` 表示需要授权时询问，并非每条命令都询问。`never` 表示需要审批的操作直接拒绝，并非自动批准。完全访问也不授予 root 或管理员身份，不绕过其他独立拒绝规则；此模式不提供受限模式的文件隔离保证。第一版是否开放它仍是提案，采用真实沙箱不等于用户已同意关闭入口。

默认方向由原来的“命令逐次确认”调整为“沙箱内自主执行，扩大权限时审批”。`npm test`、Node、Python 和 Shell 脚本都运行在当次策略下，不能仅凭命令名称或前缀视为安全。文件可写范围也不等于破坏性操作的风险审核，工作区内删除等操作可以另由工具策略要求确认。

权限配置按 Session 保存。每次调用固定策略版本和本次授权；切换模式影响后续调用，不声称已经运行的进程会即时收紧权限。收紧运行中命令的权限需要停止该命令，再在新策略下显式启动。

### 9.3 文件、凭据与网络边界

提议用户选定 Workspace 后授予普通项目文件的读取权限，写入由当前预设决定；受限模式还需配置运行时、系统库和可执行文件所需的最小读取范围。额外用户目录的读取或写入需要明确授权，不能通过默认开放整个用户主目录来满足运行依赖。

常见敏感文件（如 `.env`、私钥和凭据配置）默认需要单独确认；Praxis 自己管理的认证材料不通过模型工具开放。命令不继承宿主全部环境，不传入 Praxis 或模型密钥。受限命令的文件规则也必须落实已声明的保护范围，不能只在 `fs.read` 中拦截，却允许 Shell 读取相同受保护文件。

文件工具校验真实路径及资源身份，处理符号链接、路径大小写和 Windows 路径别名；修改已有文件时记录基线摘要，发现外部修改则要求重新读取。应用层路径检查不构成任意代码的内核隔离。命令执行则由系统沙箱限制文件效果及其子进程；硬链接和路径替换等平台边界需要验证并如实报告。

读写路径、保护路径、网络访问与进程控制是独立策略维度。DSH 的三个模式主要表达文件修改范围，不能据此声称网络或敏感读取已经隔离。Praxis 提议命令默认禁止联网，需要时授予本次执行一般网络权限，第一版不宣称域名级隔离；受保护 Host 通道仍不可访问。一旦策略声明禁止某类访问，后端就必须执行，否则拒绝调用。命令联网策略不限制 Host 的模型与认证请求。只读也不保证没有远程副作用。

### 9.4 操作系统后端与失败处理

macOS、Windows、Linux 均为第一版支持目标。共享策略接口与结果字段，底层适配和验证分别完成。TypeScript 负责策略与调度，允许使用系统命令、原生辅助程序或绑定实现限制，不要求仅靠 Node.js 完成内核控制。

| 平台 | 候选实现 | 需要验证的限制 |
| --- | --- | --- |
| macOS | Seatbelt / `sandbox-exec` | 策略有效性、读写与保护路径、子进程继承，以及系统版本兼容性；不能直接照搬仅限制写入的配置 |
| Linux | Bubblewrap，第一版不自动退回 Landlock | 内核与用户命名空间支持、挂载与链接访问、网络及子进程限制 |
| Windows | AppContainer + 明确资源 ACL；Job Object 管理进程生命周期 | 开发工具兼容、路径别名、重解析点、读取与网络保护、ACL 授权及回收；Job Object 本身不等于文件沙箱 |

这张表记录候选机制，尚未承诺具体依赖和最低系统版本。实现前按支持的系统版本、架构和策略验证后端；DSH 的 Windows 后端及部分 Landlock ABI 报告部分执行能力，不能直接将其当作完整满足 Praxis 策略的证明。

后端接口、默认网络规则、进程逃逸验证及支持矩阵提案见[沙箱与工程交付详细设计](2026-11-02-praxis-sandbox-delivery-design.md)。

后端报告名称、可用状态、各限制维度的支持情况及实际执行范围。不能用一个不加解释的 `full` 标签代表文件、网络、进程和凭据均已隔离。启动检查与每次策略适配均需验证必要能力；依赖缺失、配置失败或策略无法落实时返回 `SANDBOX_UNAVAILABLE` 或明确的策略不支持错误，命令不启动。不得悄悄退回普通宿主执行。

执行结果区分普通命令失败、策略拒绝、沙箱启动失败，以及结果未知。沙箱拒绝某次文件访问不代表整个命令此前没有产生副作用；重新申请权限和重试时需要考虑已完成的部分，不自动以扩大权限重跑整条命令。沙箱不是事务，也不会回滚已允许的文件修改。

### 9.5 单次授权、审计与恢复

优先申请具体的额外读写路径或网络权限；请求完全无沙箱执行必须作为独立、明确的选择，不能把某个文件授权隐式转换成全局访问。审批展示实际命令、参数、工作目录、当前沙箱状态和申请范围，不能只显示模型给出的解释。文件变更审批展示路径和可用的 diff。

单次授权绑定 `sessionId`、`toolCallId`、规范化参数摘要、cwd、策略版本、资源范围和有效期，执行前重新验证并只消费一次。修改参数、切换相关权限、取消或退出使旧授权失效。批准一次不改变 Session 的长期预设；需要长期切换时由独立的用户操作完成。

Session 记录权限选择及版本、审批请求和结果、执行所使用的策略和沙箱后端。Checkpoint 引用当前权限状态；恢复时重新检查平台能力，不重放已使用的授权，也不恢复仍可消费的旧审批。没有可用审批渠道或用户拒绝时不执行待授权操作。

模型审核不是系统沙箱的替代品。第一版不以 DSH 实验性 Auto review 作为必要能力；以后加入时可作为额外执行前检查，其允许结果不能自行扩大内核权限。

### 9.6 第一版内置工具提案

完整参数、结果、并发约束、预算、界面及验收要求见[内置工具详细设计](2026-11-02-praxis-tools-design.md)。第一版建议包含 13 个核心内置工具；启用 MCP 后可增加 3 个桥接工具和按需选中的服务器工具。内部 ID 使用命名空间，模型名称通过显式映射使用 `fs_read` 等下划线名称。

| 工具 | 功能及约束 |
| --- | --- |
| `fs.list` / `fs.find` / `fs.search` | 列举、按名称查找和内容检索；限制结果大小，遵守读取范围 |
| `fs.read` | 分段读取文本，检查敏感文件策略 |
| `fs.write` / `fs.apply_patch` | 创建或修改文件，检查写入范围、覆盖意图和文件基线 |
| `process.exec` | 经统一权限与沙箱执行器启动命令，支持超时、取消和输出上限 |
| `process.read` / `process.list` / `process.cancel` | 列举或通过执行 ID 读取、取消本会话所属命令，不接受任意系统 PID |
| `task.update_plan` | 版本化更新任务计划，保留跨 turn 进度；计划不是权限授权或执行证明 |
| `user.ask` | 询问需求与缺失信息，等待客户端答复；不代替权限审批 |
| `artifact.read` | 通过受控产物 ID 分段读取大输出，校验归属与读取权限 |

工具必须有输入 Schema、结果 Schema、调用与执行 ID、取消信号和副作用分类。命令默认使用程序与参数数组，管道和重定向通过显式 Shell 模式表达；两种方式执行的项目代码均受同一策略限制。结果区分成功、运行中、失败、拒绝、取消、超时和状态未知。

较大的 stdout/stderr 保存为本地产物，模型获得受权限控制的读取引用和必要摘要。截断需明确标记，流缓冲必须有界。运行中命令不脱离所属 Host，用户退出应用仍按第 5 节停止全部受管理执行。

MCP 工具进入同一 ToolExecutor、权限和审计管线；远端标记只读不自动批准，MCP 资源不能代替本地文件观察，HTTP 成功也不等于业务成功。详见[MCP 接入](2026-11-02-praxis-mcp-design.md)和[MCP 权限与恢复](2026-11-02-praxis-mcp-security-design.md)。

## 10. 会话存储、上下文与恢复

### 10.1 原始记录与有效上下文

Agent 使用追加式 Session 事件日志作为执行事实来源，并维护可重建的状态投影。事件包含 `sessionId`、递增 `sequence`、事件类型、时间、关联请求或工具 ID、Schema 版本。

至少记录输入接纳、输入领取、turn/step 边界、工具计划与结果、任务计划版本、提问与答复、权限变更、审批、实际沙箱执行策略、进程终态、完整模型回复、压缩提交和运行终态。模型文本增量作为临时流发布，按批次保存部分回复；不必把每个字符单独写成数据库事件。

Context View 是模型可见历史，与原始事件日志分开。压缩产生新的上下文版本，记录摘要、被覆盖区间、保留消息和源版本；成功提交前继续使用旧版本。摘要属于有损表示，原始事件保留。

工具请求及其结果必须成组进入上下文。工具输出中的内容作为数据处理，不升级为系统指令。系统约束、用户仍有效的要求和最近执行状态优先保留。

### 10.2 持久化

提议服务端使用 PostgreSQL 存用户、Praxis Key 元数据、Web Chat 会话及加密模型配置；本地使用 SQLite 存桌面 Chat/Agent 和 CLI Agent Session、索引，大输出使用文件存储。

每次接纳消息，在一个事务中保存请求去重记录和输入事件；持久化成功后才返回 accepted。对同一个 `requestId`、同一个提交作用域重复请求返回原结果；相同 ID 携带不同内容报冲突。

Checkpoint 保存某个 sequence 的运行状态、输入队列、有效上下文版本、权限状态及版本、工具状态引用及格式版本。恢复为“快照 + 后续事件重放”，重放不触发模型和工具，不重新激活旧的单次授权。

### 10.3 中断恢复

重启只恢复可见历史和中断状态，不自动恢复工作。用户显式继续后再接纳新 turn。

退出时尚未领取的 queue 和 steer 输入保留为 suspended；重启或恢复 Session 不把它们自动放回活动队列。用户继续当前任务，仅接纳这次继续指令；旧 pending 输入在界面列出，由用户逐条或显式批量重新提交。未领取的 steer 不会自动注入新的 turn。已经领取的输入保留在历史中，继续时参考历史与当前文件状态，不重放历史工具动作。

工具副作用与数据库事务无法天然构成原子操作。先保存执行意图，再执行，再保存结果；崩溃可能落在执行成功但结果未落盘的间隙。此时标记 unknown，根据文件摘要、操作标识等核对；命令执行不得默认重跑。

第一次恢复可以由用户说明继续方向，再由 Agent 读取当前文件确认状态。不得承诺任意工具 exactly-once，也不以“存在 checkpoint”作为重复执行安全的证明。

### 10.4 第一版各端独立

桌面与 CLI 使用不同本地数据目录；桌面 Chat 和 Agent 在本机按 kind 分开，CLI 只有 Agent。Web Chat 保存在服务端，使用用户 Web 作用域，同一账号刷新页面或在另一浏览器登录仍可查看其 Web 历史。

本地 Session 绑定用户和客户端安装/profile 作用域，重登同一账号可查看本机对应历史；更换安装实例不自动继承历史。本地内容不因共享模型配置上传至服务器，第一版不提供会话跨端迁移、同步或接管。不同账号不混用记录。

`clientScopeId` 仅表示数据分组，不能代替用户鉴权；所有读取与写入仍按用户归属校验。不同 Web 页面同时对一个 Chat 会话生成时，遵循第 7 节的单次生成约束，不据此引入平台的控制端租约。

模型提供商配置是用户级共享设置，不受上述会话分组限制。共享提供商及 Key 不同步会话历史、工作目录或正在运行的任务。

## 11. 协议与事件

服务器 API 负责账号、Key、Web ChatBot、统一模型设置与专用凭据交付；本地 Host 协议负责 Agent 和桌面 Chat。共享基础类型，但不把任意本地工具能力暴露为无需鉴权的远程接口。

建议本地协议采用带版本的 JSON-RPC 风格请求/响应与通知，第一版通过 stdio 传输。请求和响应都做运行时 Schema 校验，TS 类型不能代替边界检查。

| 方法 | 语义 |
| --- | --- |
| `host/initialize` | 版本、能力和父进程实例握手 |
| `session/create` / `list` / `read` | 创建及查看本端会话 |
| `session/prompt` | 持久化接纳输入，支持 queue / steer |
| `session/cancel` | 请求取消当前 turn；pending 输入如何处理由显式字段决定 |
| `session/continue` | 对已中断会话显式提交继续意图 |
| `session/set-permissions` | 用户修改当前会话权限，产生持久事件并使相关旧审批失效 |
| `approval/respond` | 回应特定审批，不接受过期或参数不匹配的响应 |
| `question/respond` | 回应特定用户问题，验证题目版本和待答状态，不生成执行授权 |
| `session/subscribe` | 从已提交 sequence 订阅可回放事件 |
| `host/shutdown` | 停止接纳、取消、保存并退出 |

RPC `id` 匹配一次通信；`requestId` 用于业务去重；两者不可混用。接纳响应不代表任务完成。

持久事件携带 sequence，客户端断连按游标重放并去重。文本 delta 带 attempt ID 和局部序号，完整消息提交后替换对应临时显示；不能把临时增量混入持久游标并承诺全部可重放。

慢客户端的输出缓冲必须有限。允许合并临时 delta，持久事件缺失时要求重同步。客户端通过事件更新状态，不凭某句话猜测“任务完成”。

完整方法、版本握手、订阅竞态、重新生成及关闭合同见[Host、Chat 与协议设计](2026-11-02-praxis-protocol-chat-design.md)。

## 12. 插件设计

第一版提供受信任 Host 插件，覆盖模型 Provider、Agent 工具、命令和受控执行钩子。ChatBot 不挂载操作型工具插件。UI 扩展接口可以预留，但外部 UI 插件加载不作为首个闭环的前置条件。

插件清单包含 `id`、版本、SDK 兼容范围、入口、支持模式和声明能力。宿主根据配置实际授予能力，清单本身不是授权。

激活时验证并原子发布能力；停用时禁止新调用，等待或取消该插件的活动调用。第一版通过 Host 重启完成代码卸载和更新。活动 turn 固定 Provider、插件版本和核心工具定义；MCP 目录按服务器首次发现固定 generation，后续只在 step 边界调整被选子集，每次请求保存独立 ToolSetSnapshot，不在审批后热换实现。

插件只能依赖稳定 SDK，不能依赖 Runtime 私有类或数据库表。宿主提供带作用域的存储、凭据引用、日志和工具注册接口；插件不得从模型参数选择用户身份或任意其他会话。

同进程可信插件本质上拥有宿主代码权限，SDK 约束不构成恶意代码沙箱。它们应经 Host 的文件和命令执行接口完成操作，不因声明“只读工具”跳过策略检查；但这不是对恶意插件的强制隔离。模型生成的代码只经命令沙箱运行，不动态导入为 Host 插件。将来接入不受信任插件时，另外设计受限执行环境；简单 fork 子进程只隔离故障，不足以限制权限。

MCP 作为独立的外部能力接入模块，不替代整个插件系统。两份详细设计分别覆盖[MCP 接入、协议与上下文](2026-11-02-praxis-mcp-design.md)和[MCP 认证、沙箱、审计与验收](2026-11-02-praxis-mcp-security-design.md)。本地 MCP 程序默认按操作启动并回收；远程请求由本机 Host 直连，不经 Praxis Server 代理。

Manifest、SDK、生命周期、工作区身份与跨进程占用、配置优先级见[插件、工作区与配置设计](2026-11-02-praxis-plugins-config-design.md)。

## 13. 工程边界与选型提案

建议使用 Node.js、pnpm workspace 和 TypeScript strict。Web 与桌面渲染层使用 React + Vite；桌面外壳使用 Electron；服务端使用 Hono 模块化单体。它们承担界面与基础设施，Agent 循环仍自行实现。

这些是实现建议，不是已获确认的全部技术选型；具体版本在实施计划中核对并锁定。

目标逻辑目录如下，按开发计划逐步创建；当前源码与可运行状态以根 README 为准：

```text
apps/
  server/              # 认证、ChatBot、用户配置
  web/                 # ChatBot Web
  desktop/             # Electron 宿主及双模式入口
  cli/                 # Agent CLI
  agent-host/          # 本地 Host：Agent + 桌面 Chat 的组装入口
packages/
  contracts/           # 消息、事件、Schema、协议版本
  client-server/       # 认证和 ChatBot API 客户端
  client-host/         # 本地 Host 协议客户端
  ui/                  # Web / 桌面共享展示
  chat-runtime/        # 无工具的对话运行方式
  agent-runtime/       # Session、队列、Turn / Step
  model-core/          # Provider 接口及标准消息
  auth-client/         # 本地认证、凭据桥和统一配置使用
  config/              # 配置解析、来源及生效版本
  workspace/           # 项目身份、信任与跨进程占用
  context/             # 预算、上下文视图与压缩
  tools/               # 注册、执行、取消及标准结果
  permissions/         # 策略解析、单次授权与审批审计
  sandbox/             # 统一后端接口及 macOS / Windows / Linux 适配
  process-runtime/     # 受管理进程、执行 ID、输出游标与清理
  storage-local/       # SQLite 与文件产物
  storage-server/      # 服务端持久化
  plugin-sdk/          # 公共扩展契约
  plugin-runtime/      # 插件加载与生命周期
  mcp-core/            # MCP 目录、操作状态与工具选择
  mcp-client/          # 新旧协议与受控 stdio / HTTP 适配

  tools-shell/
  tools-task/
```

Runtime 依赖接口，不能直接依赖 React、Electron、HTTP 请求对象或具体数据库驱动。应用入口负责依赖组装。首期可合并较小包，不能为了目录对称提前制造大量抽象。

首发操作系统已确定为 macOS、Windows、Linux，桌面端和 CLI 均需覆盖。最低系统版本、CPU 架构和沙箱运行依赖在实施计划中明确。原生沙箱、命令取消、凭据存储和桌面打包必须在实际支持的系统验证，不能把 macOS 测试视为 Windows 或 Linux 支持证明。

## 14. 平台化扩展边界

当前资源显式绑定用户和工作目录，身份来自认证上下文而不是模型或客户端任意字段。暂不引入空壳租户业务；以后将服务端数据迁移到租户作用域，并补齐租户资源授权、凭据隔离及执行隔离。

远程化时把 Host 协议适配到有认证的网络传输。未来的单端控制需要独立的控制租约，包含持有客户端、有效期和递增 epoch；所有修改命令验证当前租约，旧控制端失去资格后不能继续写入。只读订阅不授予控制权。

一个活动执行、一个控制客户端和多个观察者是三个不同约束。不要用“线程 busy”或“存在 SSE 连接”替代控制权。

未来控制端断开是否停止平台任务尚未决定；不能从第一版本地退出规则推导所有远程生命周期行为。

## 15. 验收标准

| 编号 | 场景与预期 |
| --- | --- |
| V01 | Web 提交 HelloWorld 页面需求，仅显示解释、代码和操作步骤，不写入用户文件。 |
| V02 | ChatBot 第二轮要求改颜色，参考此前代码回答，仍不执行工具。 |
| V03 | 本地 Agent 创建 `index.html`，文件实际存在且内容符合要求。 |
| V04 | 下一轮要求改颜色，读取并修改既有文件，工具失败时不报告成功。 |
| V05 | Agent 执行测试并区分成功、非零退出、超时和取消。 |
| V06 | queue 与 steer 在约定边界生效，不并行推进同一 Session。 |
| V07 | 同一 requestId 重传只接纳一次；内容不一致报冲突。 |
| V08 | 用户拒绝审批后对应操作未执行；过期审批不能执行。 |
| V09 | 正常退出和父进程异常退出后，受管理 Host 与命令不会继续作为后台任务运行。 |
| V10 | 崩溃重启保留历史并标记中断；不会自动重跑未知结果命令。 |
| V11 | 长历史触发压缩后保留原始事件；工具请求与结果保持配对；失败不提交无效摘要。 |
| V12 | Praxis 管理的 Key 不混用，不经配置与凭据流程进入模型上下文、Session、普通日志或前端读回响应；已知秘密脱敏及敏感文件权限规则可验证。 |
| V13 | Web 与桌面 ChatBot 的取消只影响对应生成；其他用户会话和服务器继续运行。 |
| V14 | 按第一版范围实现各端会话隔离；共享物理工作目录时能识别写入冲突。 |
| V15 | 不兼容插件拒绝加载，ChatBot 不获得 Agent 工具，停用有明确清理结果。 |
| V16 | 网络中断、模型错误、数据库写失败和慢订阅者都有可观察结果，不伪报已接纳或已完成。 |
| V17 | 同一用户只配置一次模型提供商及厂商 Key，Web ChatBot、桌面 ChatBot / Agent、CLI Agent 均可引用，无需按模式或客户端重复填写。 |
| V18 | 更新或删除统一提供商配置后，各端后续使用按配置版本刷新或提示配置不可用；不出现一端已删除、另一端仍把陈旧配置当有效配置的分叉。 |
| V19 | macOS、Windows、Linux 上分别通过真实进程验证只读和工作区可写策略；普通 Shell、解释器及其子进程不能绕过声明的文件限制。 |
| V20 | 沙箱依赖不可用或无法执行所需策略时命令不启动；不会自动切换完全访问，界面与日志报告具体原因。 |
| V21 | 范围内的普通命令不要求逐条确认；扩大权限需绑定本次调用的授权，参数、cwd、策略或范围改变后旧授权不能使用，授权不能重复消费或重启后恢复。 |
| V22 | 真实路径、符号链接及各系统的链接和别名场景按实际支持能力验证；受保护文件不能通过替换文件工具为 Shell 读取而绕过已声明的受限策略。 |
| V23 | 网络规则独立于文件预设验证；若配置禁止联网，真实子进程连接必须被阻止，后端不能落实时应拒绝执行该策略。 |
| V24 | 权限与审批审计可重建；模式切换不伪称已改变既有进程权限；命令被沙箱拒绝后不自动扩大权限重跑或伪称已回滚部分副作用。 |
| V25 | 内置工具遵守详细设计中的版本保护、命令等待/超时区分、输出游标、计划、提问及产物规则；按其 T01–T15 执行针对性验证。 |
| V26 | 桌面 Chat/Agent 与 CLI 的模型请求直连厂商；Praxis Server 仅承担本地客户端的认证、统一配置和凭据交付，不接收本地对话正文。Web Chat 由服务端调用模型。 |
| V27 | 原事件、Context View、Request Snapshot、Recovery Checkpoint 各自可核对；快照重放不执行工具，候选摘要失败不改变有效上下文。 |
| V28 | 普通配置查询不返回厂商 Key，每个新 turn 在线核对配置；重试、限额、插件失败、配置冲突及工作区占用均有明确处理。 |
| V29 | Host 协议版本、订阅回放和慢客户端不破坏控制响应；Chat 重新生成只选择一个候选，不引入 Agent 操作能力。 |
| V30 | MCP 按明确版本与能力子集接入，工具按需暴露、资源按需读取、模板由用户选择；不改变 ChatBot 无工具边界。 |
| V31 | MCP stdio 进入三平台真实沙箱及执行位，远程凭据/目的地和数据披露受控，关闭后本地受管进程停止，远端未知效果如实记录。 |
| V32 | MCP 目录变更、OAuth、MRTR、取消、超限、数据库失败与恢复按 M01–M20 验证；不存在业务调用盲目重放或旧授权恢复。 |

验收分为纯 Runtime 单元测试、临时文件/子进程集成测试、假 Provider 协议测试和少量真实模型端到端测试。退出清理、凭据与路径边界需在 macOS、Windows、Linux 分别验证；模拟后端的单元测试不能替代系统沙箱测试。测试只能操作专用临时工作区和外部哨兵文件，不能借验证权限而触碰用户真实敏感数据。使用真实模型的测试由专用配置提供凭据，不依赖开发者私有配置。

## 16. 开发基线与验证事项

第 2 节已经确认的决定不需重复选择。以下实现提案作为开发起点；常规选择依据原型结果调整并同步文档，涉及产品边界变更时再单独确认：

1. 桌面 ChatRuntime 放在本地 Host，历史本地保存；Web 历史在服务端。三端不自动共享会话。
2. 模型配置统一管理、本地直连已确认；服务端加密存储、专用凭据交付、本地仅内存保存和每轮在线版本核验为详细方案。
3. 本地客户端必须 Praxis 认证，使用 15 分钟身份凭证；吊销限制后续 turn 启动，不在第一版远程强制终止活动 turn。
4. 第一版账号采用管理员创建，不提供公开注册、找回邮件或第三方登录。
5. 关闭最后一个桌面窗口即退出；恢复必须由用户显式继续，旧待处理输入另行显式重新提交。
6. 真实操作系统沙箱已确认；提议默认工作区可写、命令网络禁止、范围内自主执行，扩大权限及敏感文件操作需单次批准；完全访问入口默认不开启，仍为高级方案提案。
7. macOS、Windows、Linux 已确定；最低系统版本、CPU 架构和具体后端依赖待实施计划核对。可信 Host 插件优先，不承诺隔离任意同进程插件。
8. 内置工具详细设计中的 13 个工具、参数和限额为提案；特别包括单文件结构化补丁、活动命令期间限制写入、turn 结束清理命令及跨 turn 保留计划。
9. 本轮详细合同覆盖执行、历史/上下文、认证/模型、协议/Chat、插件/工作区、原生沙箱、诊断/迁移/发布及 MCP 接入闭环。默认预算和工程候选需要随原型验证调整，变化须保持已确认产品边界并同步文档。
10. MCP 作为可选 Agent 模块的交付提案，包括按操作回收 stdio、新旧两版协议、文本资源/用户模板、OAuth/表单交互；不支持跨调用进程内状态、sampling、Tasks 和 MCP Apps。其他既有后续扩展尚未因此自动完成详细设计。

按[开发计划](../plans/2026-11-03-praxis-development-plan.md)启动工程与可独立验证的核心开发，UI 按[设计基线](2026-11-03-praxis-ui-design.md)实现。各平台真实沙箱、退出清理和凭据存储验证是对应功能的交付门槛；本文件不是实施已完成的证明。
