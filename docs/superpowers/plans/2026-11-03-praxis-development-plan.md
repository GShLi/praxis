# Praxis 第一版开发计划

日期：2026-11-03。依据[总体设计](../specs/2026-11-02-praxis-design.md)、[UI 基线](../specs/2026-11-03-praxis-ui-design.md)及各模块详细合同。现有设计足够启动开发；本计划区分实施步骤、当前成果与需要真实环境验证的交付门槛。

## 1. 当前状态

- 设计及 MCP 合同已形成，UI 已确定参考 ChatGPT/Codex。
- `praxis/` 已初始化独立 Git 仓库，分支 main；沿用本机作者/提交者身份，不覆盖 user.name/user.email。
- 当前仅有设计、项目说明和忽略规则，还没有可运行应用、package.json 或依赖锁文件。
- 本机已观测到 Node v22.15.0、pnpm 11.9.0；这是环境记录，不是已验证的最终依赖组合。

原生沙箱、退出清理、系统凭据存储和发行依赖必须分别验证。它们限制对应功能何时开放，不阻止先建立工程、实现协议/事件/存储或完成 UI 组件。

## 2. 开发原则

按照已有产品边界推进，常规实现选择使用详细设计的提案作为起点；发现矛盾或平台不可行时更新相应设计及实现记录，不把候选机制标成已支持。业务与 Agent 循环使用 TypeScript 自研，协议/数据库/UI 等基础库按职责采用。

每个阶段产出可运行、可检查的结果，完成相关验证后提交。先检查差异和秘密材料，再用本机 Git 身份提交；不设置临时作者、不伪造共同作者、不关闭既有签名策略。提交是本地版本记录，不自动创建远端或推送。

避免一次创建全部空包。先建立会实际使用的边界，再随功能拆分。每个新增脚本在 README 说明用途与环境要求；没有实现的命令不写成可执行使用指南。

## 3. 阶段与完成条件

| 阶段 | 实施内容 | 完成条件 |
| --- | --- | --- |
| P0 工程基座 | 核对 Node/TS/前端/桌面依赖兼容，pnpm workspace、strict TS、检查脚本、锁文件、最小入口与 CI；建立共享 UI tokens | 干净安装可重现，类型/基础检查可运行，入口诚实报告当前能力 |
| P1 平台执行原型 | macOS/Linux/Windows 沙箱后端合同、受管子进程、父死亡清理、执行位、凭据存储探测 | 各平台在临时目录验证允许/拒绝操作与子孙回收；不能支持的策略拒绝执行 |
| P2 核心与本地闭环 | 领域 Schema、Session 事件/投影/SQLite、Host stdio、队列、取消、checkpoint；Fake Provider 驱动文件工具 | 无厂商 Key 可验证创建/修改 HelloWorld 文件、多轮、幂等、中断与手动继续；失败不伪报完成 |
| P3 模型与身份 | DeepSeek 流式适配、服务端账号/API Key、统一 Provider/凭据交付、PostgreSQL、ChatRuntime | 模拟协议故障通过；由专用配置做少量真实模型验证；客户端直连且普通接口不读回 Key |
| P4 Agent 完整运行 | 13 个核心工具、真实命令、权限/审批、queue/steer、计划/提问、上下文压缩与产物 | CLI 可完成多轮本地任务；原历史保留，超限/未知副作用有明确终态，退出停止执行 |
| P5 Web 与桌面交付 | ChatGPT 风格 Chat、Codex 风格 Agent 工作区；登录/设置、事件重放、diff/输出、恢复；Electron 主进程/Host 组装 | Web 仅 Chat；桌面双模式；所有操作由真实服务状态驱动，三端会话独立 |
| P6 插件与 MCP | 可信 SDK、版本化注册、stdio/HTTP 新旧协议、工具选择、资源/模板、OAuth、事件与恢复 | 通过 M01–M20 对应 fixture；MCP 本地进程走真实沙箱，业务失败不盲目重试 |
| P7 发布验证 | 全量场景回归、迁移/备份、平台打包/签名、安装升级与诊断、使用文档 | 支持矩阵与测试证据一致；通过对应平台的安装、退出、隔离和数据恢复检查 |

P1 和 UI 组件可与 P2/P3 并行探索；受影响命令和 MCP stdio 只有对应系统 P1 门槛通过后才开放。P5 的完整交付依赖实际 Runtime，但无需等待所有后端工作才开始页面组件。P6 可先用 fixture 开发，不连接用户真实外部账号做写入测试。

## 4. 第一个开发切片

从 P0 开始，目标是一个能安装、检查并启动最小入口的工程：

1. 锁定包管理器与支持 Node 版本，建立根 manifest、workspace、基础 TypeScript 配置和统一检查入口。
2. 建立 contracts 与最小 CLI/Host 握手，协议未知版本/无效消息得到明确错误，退出不留下 Host。
3. 增加最小共享 UI tokens 和 Chat/Agent 布局组件；开发样例只能展示明确的测试事件，不冒充已接真实模型。
4. 把实际命令、依赖约束、运行方式与已通过检查写入根 README，完成一个独立提交。

然后以 P2 的假模型文件闭环推进，同时做 P1 平台验证。真实 Key 接入、远端权限和生产数据不作为工程初始化的前置条件；未实现模型服务时界面显示当前不可用，不制造假回复。

## 5. 测试与提交节奏

领域状态、去重、权限与压缩采用有针对性的自动测试；本地文件、SQLite、stdio 和命令用临时环境集成测试；模型和 MCP 先使用受控协议服务注入错误。原生沙箱及进程树停止必须使用各 OS 真实进程验证。

每次提交前运行与差异对应的检查并检查 git diff。只改设计/说明时验证链接、示例、编号与 diff 格式，不为文档跑无关模型或平台全套测试；代码增加后才执行对应构建、类型、行为和 UI 检查。阶段性验证结果记录在提交说明/开发记录，未跑项目明确列出。

建议提交单位为工程基座、协议合同、存储事务、一个工具或一个完整用户流程；发生修复则单独提交。不要为机械改行制造大量提交，也不等全部功能做完才提交一次。用户明确要求的本机 Git 身份持续有效。

## 6. 启动条件与交付门槛

当前可以开始 P0 与可独立验证的核心开发。无需先完成独立 UI 设计项目；按 UI 基线完成真实组件，再通过具体页面检查收敛尺寸与交互。

第一版可发布仍以 V01–V32、T01–T15、M01–M20 及 UI 流程验收为依据。单机测试、模拟沙箱或静态 UI 不能证明三平台完整可用。后续租户、平台远程执行、多端控制等不进入本次开发里程碑。
